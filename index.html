Java Architecture & Compilation

Write Once, Run Anywhere (WORA) — Java source code is compiled to platform-neutral bytecode (.class files), which runs on any device that has a Java Virtual Machine (JVM) . The JVM acts as the translation layer between bytecode and the native machine code of the host OS.

Compilation Pipeline 

 ┌─────────────┐      javac       ┌──────────────┐      JVM       ┌──────────────────┐
 │  Hello.java │  ─────────────▶  │  Hello.class │  ──────────▶  │  Machine Code    │
 │  (Source)   │   Java Compiler  │  (Bytecode)  │  ClassLoader  │  (OS / Hardware) │
 └─────────────┘                  └──────────────┘               └──────────────────┘
        ▲                                                                   ▲
  Human-readable                                                    Platform-specific

ClassLoader Subsystem

ClassLoaders load .class files into the JVM on demand. They follow the delegation model : a child loader always asks its parent first before loading itself. 

  Bootstrap ClassLoader  (native C++, loads rt.jar / java.base)
         │
  Extension ClassLoader  (loads from $JAVA_HOME/lib/ext)
         │
  Application ClassLoader  (loads from -classpath / CLASSPATH)
         │
  Custom ClassLoader  (user-defined, used in frameworks/containers)
  • Bootstrap — highest trust, loads core classes like java.lang.Object , java.lang.String .
  • Extension (Platform in Java 9+) — loads from jre/lib/ext ; replaced by module system in Java 9.
  • Application — loads your application's classpath classes.

JIT Compiler & HotSpot

The JVM starts by interpreting bytecode instruction-by-instruction. The JIT (Just-In-Time) Compiler monitors execution and identifies "hot spots" — code paths executed many times. It compiles those paths to native machine code for a dramatic speed boost.

  • C1 (Client Compiler) — fast compilation, light optimizations. Good for short-lived processes.
  • C2 (Server Compiler) — deeper optimizations (inlining, loop unrolling). Better peak throughput.
  • Tiered Compilation (default Java 8+) — starts with C1, promotes hot code to C2.

Bytecode Verification

Before execution, the JVM verifier checks .class files to ensure:

  • The class file format is valid and has correct magic bytes ( 0xCAFEBABE ).
  • No stack overflows/underflows occur in bytecode.
  • Type safety is maintained (no illegal casts).
  • No access to private members from outside the class.

This is Java's first line of defence against malicious or corrupt class files.

Garbage Collection

Mark-and-Sweep is the foundational GC algorithm:

  1. Mark — starting from GC roots (local vars, static refs), traverse the object graph and mark reachable objects.
  2. Sweep — reclaim memory occupied by unmarked (unreachable) objects.
  3. Compact (some collectors) — move live objects together to reduce fragmentation.
Collector Algorithm Stop-the-World? Best For
Serial GC Mark-Sweep-Compact Yes (full) Single-threaded / small heaps
Parallel GC Multi-threaded M-S-C Yes (full, shorter) Throughput-focused apps
G1 GC Region-based, incremental Short concurrent pauses Balanced throughput + latency
ZGC Load-barrier, concurrent <1ms pauses Ultra-low latency, large heaps
Shenandoah Concurrent compaction <1ms pauses Low-latency, Red Hat JDK

Static Keyword

The static keyword means a member belongs to the class , not to any particular instance. Static members are loaded once when the class is loaded and shared across all instances.

Static Variables

JAVA 
public class Counter {
    static int count = 0;   // class-level, shared by all instances
    int id;                    // instance-level, unique per object

    Counter() {
        count++;               // increments the single shared copy
        this.id = count;
    }
}

Counter a = new Counter(); // count = 1, a.id = 1
Counter b = new Counter(); // count = 2, b.id = 2
System.out.println(Counter.count); // 2 — access via class name

Static Methods

JAVA 
public class MathUtils {
    public static int square(int n) {
        return n * n;
    }
    // static methods CANNOT access instance variables / methods directly
    // static methods CANNOT use 'this' or 'super'
    // static methods CAN call other static methods
}

int result = MathUtils.square(5); // 25 — no object needed
⚠️ Warning
Calling this.staticMethod() compiles (it resolves to the class), but it's bad practice — always use ClassName.staticMethod() for clarity.

Static Blocks (Initializers)

JAVA 
public class Config {
    static final Map<String, String> DEFAULTS;

    static {
        // runs once when class is first loaded by ClassLoader
        DEFAULTS = new HashMap<>();
        DEFAULTS.put("host", "localhost");
        DEFAULTS.put("port", "8080");
    }

    static int x;
    static int y;

    static { x = 10; }   // multiple static blocks allowed
    static { y = x * 2; } // executed in order of appearance
}

For a class: 1) static variables & blocks (in textual order) → 2) instance variables & instance initializers → 3) constructor.

Integer Cache (-128 to 127)

The JVM caches Integer objects for values in the range -128 to 127 inclusive. Integer.valueOf() returns the same cached object for values in this range, so == returns true .

JAVA 
Integer a = 127, b = 127;
System.out.println(a == b);   // true  ← cached, same object

Integer c = 128, d = 128;
System.out.println(c == d);   // false ← outside cache, new objects

// Why? JLS 5.1.7 mandates caching for -128..127
// Always use .equals() to compare Integer values!
💡 Cache Extension
You can extend the upper cache limit with JVM flag: -XX:AutoBoxCacheMax=500 . Only the upper bound is configurable; -128 is always the lower bound.

Strings in Java

String is a final class in java.lang . Internally it's backed by a char[] (pre-Java 9) or byte[] with encoding flag (Java 9+ compact strings). Strings are immutable — once created, the content cannot change. Any "modification" creates a new object.

Literal vs new String()

JAVA 
String a = "hello";           // goes to String Pool
String b = "hello";           // reuses same pool object
String c = new String("hello"); // new heap object, NOT in pool

System.out.println(a == b);        // true  (same pool ref)
System.out.println(a == c);        // false (different objects)
System.out.println(a.equals(c));   // true  (same content)

// intern() moves a heap string into the pool:
String d = c.intern();
System.out.println(a == d);        // true  (d is now the pool ref)

Inheritance & Polymorphism

Java supports single inheritance — a class can extend only one class. This avoids the diamond problem (solved via interfaces with default methods). Use extends for classes, implements for interfaces.

  • IS-A (inheritance): Dog extends Animal → Dog IS-A Animal
  • HAS-A (composition): Car has an Engine field → favour composition over inheritance

Method Overriding

JAVA 
class Animal {
    public String sound() { return "..."; }
}

class Dog extends Animal {
    @Override                     // annotation catches typos at compile time
    public String sound() {       // same name, same params
        return "Woof";
    }
}

// Overriding rules:
// 1. Same method signature
// 2. Return type: same OR covariant (subtype) — e.g. Dog overrides Animal getClone()
// 3. Access modifier: same or WIDER (e.g. protected → public, never narrower)
// 4. Exception: can throw fewer/narrower checked exceptions (not more/wider)
// 5. Cannot override static, final, or private methods

Runtime Polymorphism (Dynamic Dispatch)

JAVA 
Animal a = new Dog();  // upcast: Dog IS-A Animal
System.out.println(a.sound()); // "Woof" — resolved at RUNTIME via vtable

// Downcasting (explicit, risky without instanceof check):
if (a instanceof Dog d) {     // pattern matching (Java 16+)
    d.fetch();                // no explicit cast needed!
}

equals() and hashCode() Contract

🔑 The Contract
If a.equals(b) is true , then a.hashCode() == b.hashCode() MUST also be true . (The reverse is not required.) Breaking this contract causes bugs in HashMap, HashSet, etc.
JAVA 
class Point {
    int x, y;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;
        return x == p.x && y == p.y;
    }

    @Override
    public int hashCode() {
        return Objects.hash(x, y); // same fields as equals!
    }
}

Concurrency vs Parallelism 

CONCURRENCY (single core — interleaving):
Core 1:  [T1]──[T1]──[T1]──[T2]──[T2]──[T1]──[T2]
          time ─────────────────────────────────────►
         Tasks appear simultaneous but take turns

PARALLELISM (multi-core — truly simultaneous):
Core 1:  [T1]──[T1]──[T1]──[T1]──
Core 2:  [T2]──[T2]──[T2]──[T2]──
          time ─────────────────────►
         Tasks run at the exact same instant
🔑 Key Concept
Key insight: Concurrency is about dealing with many things at once (structure). Parallelism is about doing many things at once (execution). You can have concurrency without parallelism (single core), but parallelism requires concurrent structure.

Amdahl's Law

🔑 Key Concept
Formula: S(n) = 1 / ( (1 − p) + p/n )

Where: S = speedup, p = parallelisable fraction (0–1), n = number of processors

Implication: If 5% of code is sequential ( p = 0.95 ), maximum possible speedup is 1/0.05 = 20× , no matter how many cores you add. Sequential bottlenecks dominate. 
p = 0.50 → max speedup: 2×
p = 0.75 → max speedup: 4×
p = 0.90 → max speedup: 10×
p = 0.95 → max speedup: 20×
p = 0.99 → max speedup: 100×   (requires truly parallel-friendly code)

Benefits of Multithreading

  • Responsiveness: UI stays reactive while background work runs (e.g., loading data)
  • Resource sharing: Threads share heap memory — no IPC overhead
  • Economy: Cheaper to create/context-switch than processes
  • Scalability: Exploit multi-core hardware; speed scales with cores for parallel sections

4.1 Synchronization

Race Condition — The Counter++ Problem

⚠️ Warning
counter++ is NOT atomic. It is 3 separate operations: READ (load counter) → MODIFY (add 1) → WRITE (store result). Two threads can interleave these steps, causing lost updates. 
Thread 1          Thread 2         counter value
READ counter=5                      5
                  READ counter=5    5
ADD 1 → 6                           5
                  ADD 1 → 6         5
WRITE 6                             6
                  WRITE 6           6   ← expected 7, got 6! Update lost!
// UNSAFE — race condition
public class UnsafeCounter {
    private int count = 0;
    public void increment() { count++; }   // NOT thread-safe!
    public int  getCount()  { return count; }
}

Critical Section & Mutual Exclusion

A critical section is code that accesses shared mutable state. Mutual exclusion ensures only one thread executes it at a time.

Intrinsic Locks / Monitors

🔑 Key Concept
Every Java object has a built-in intrinsic lock (monitor lock). When a thread enters a synchronized method/block, it acquires the object's lock. Other threads trying to enter any synchronized method on the same object are blocked until the lock is released.

synchronized Method vs Block 

public class SafeCounter {
    private int count = 0;
    private final Object lock = new Object();

    // Method-level: locks 'this' object
    public synchronized void increment() {
        count++;
    }

    // Block-level: finer-grained, specify lock object explicitly
    public void add(int n) {
        synchronized (lock) {   // only this block is protected
            count += n;
        }
        // other non-critical work here runs concurrently
    }

    // Static synchronized: locks the CLASS object, not instance
    public static synchronized void staticMethod() { /* ... */ }

    public int getCount() { return count; }
}

Reentrant Locks

Java's intrinsic locks are reentrant : a thread that already holds a lock can re-enter another synchronized method on the same object without blocking itself. 

public synchronized void methodA() {
    methodB();   // OK! same thread already holds 'this' lock
}
public synchronized void methodB() { /* ... */ }

Drawbacks of Intrinsic Locks

  • No tryLock() — cannot attempt without blocking indefinitely
  • No timeout — can wait forever
  • Cannot interrupt a thread waiting for a monitor lock
  • All waiters contend on same lock — no read/write separation

volatile Keyword

🔑 Key Concept
volatile guarantees visibility, NOT atomicity. Reads/writes to a volatile variable go directly to main memory — no CPU cache buffering. Establishes a happens-before relationship for that variable. 
public class StatusFlag {
    private volatile boolean running = true;   // visible to all threads

    public void stop()      { running = false; }  // write visible immediately
    public boolean isOn()  { return running; }    // always reads fresh value
}

// volatile is NOT enough for compound operations:
private volatile int count = 0;
count++;   // STILL a race! volatile ≠ atomic

Mutual exclusion ❌ No locking ✅ One thread at a time

ReentrantLock — Basic Pattern 

import java.util.concurrent.locks.*;

public class SafeCounter {
    private int count = 0;
    private final ReentrantLock lock = new ReentrantLock();

    public void increment() {
        lock.lock();
        try {
            count++;              // critical section
        } finally {
            lock.unlock();      // ALWAYS in finally to avoid lock leak
        }
    }

    public int getCount() {
        lock.lock();
        try { return count; }
        finally { lock.unlock(); }
    }
}

tryLock() Pattern — Avoiding Deadlock 

public boolean transfer(Account from, Account to, double amount) {
    boolean fromLocked = false, toLocked = false;
    try {
        fromLocked = from.lock.tryLock(100, TimeUnit.MILLISECONDS);
        toLocked   = to.lock.tryLock(100, TimeUnit.MILLISECONDS);
        if (fromLocked && toLocked) {
            from.balance -= amount;
            to.balance   += amount;
            return true;
        }
        return false;   // retry or abort if either lock not acquired
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return false;
    } finally {
        if (toLocked)   to.lock.unlock();
        if (fromLocked) from.lock.unlock();
    }
}

ReentrantReadWriteLock

🔑 Key Concept
Rule: Multiple threads can hold the read lock simultaneously (readers don't block each other). Only one thread can hold the write lock , and it excludes all readers. Perfect for read-heavy caches. 
ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock  = rwLock.readLock();
Lock writeLock = rwLock.writeLock();
Map<String, String> cache = new HashMap<>();

public String get(String key) {
    readLock.lock();
    try { return cache.get(key); }
    finally { readLock.unlock(); }   // multiple threads can read in parallel
}

public void put(String key, String val) {
    writeLock.lock();
    try { cache.put(key, val); }
    finally { writeLock.unlock(); }  // exclusive: no readers allowed
}

StampedLock (Java 8+) — Optimistic Reading 

StampedLock sl = new StampedLock();

double read() {
    long stamp = sl.tryOptimisticRead();   // no actual lock acquired
    double value = x;
    if (!sl.validate(stamp)) {             // was a write in between?
        stamp = sl.readLock();             // fall back to real read lock
        try { value = x; }
        finally { sl.unlockRead(stamp); }
    }
    return value;
}

Producer-Consumer with wait/notify 

public class BoundedBuffer<T> {
    private final Queue<T> queue = new LinkedList<>();
    private final int     capacity;

    public BoundedBuffer(int capacity) { this.capacity = capacity; }

    public synchronized void produce(T item) throws InterruptedException {
        while (queue.size() == capacity) {   // ← WHILE not IF (spurious wakeups)
            wait();                           // releases lock; waits
        }
        queue.add(item);
        System.out.println("Produced: " + item);
        notifyAll();                         // wake consumers
    }

    public synchronized T consume() throws InterruptedException {
        while (queue.isEmpty()) {            // ← WHILE not IF
            wait();                           // releases lock; waits
        }
        T item = queue.poll();
        System.out.println("Consumed: " + item);
        notifyAll();                         // wake producers
        return item;
    }
}
🔑 Key Concept
Always use while , never if when checking wait conditions. Spurious wakeups (thread wakes without notification) can occur. The while loop re-checks the condition and goes back to wait() if it's still not met.

Condition Variables (with ReentrantLock) 

import java.util.concurrent.locks.*;

public class ConditionBuffer<T> {
    private final Lock      lock      = new ReentrantLock();
    private final Condition notFull   = lock.newCondition();
    private final Condition notEmpty  = lock.newCondition();
    private final Queue<T> queue    = new LinkedList<>();
    private final int        capacity;

    public ConditionBuffer(int cap) { this.capacity = cap; }

    public void produce(T item) throws InterruptedException {
        lock.lock();
        try {
            while (queue.size() == capacity) notFull.await();
            queue.add(item);
            notEmpty.signal();   // wake ONE consumer specifically
        } finally { lock.unlock(); }
    }

    public T consume() throws InterruptedException {
        lock.lock();
        try {
            while (queue.isEmpty()) notEmpty.await();
            T item = queue.poll();
            notFull.signal();    // wake ONE producer specifically
            return item;
        } finally { lock.unlock(); }
    }
}

Deadlock Example 

final Object lockA = new Object();
final Object lockB = new Object();

// Thread 1: acquires lockA, then waits for lockB
Thread t1 = new Thread(() -> {
    synchronized (lockA) {
        System.out.println("T1 holds lockA, waiting for lockB");
        try { Thread.sleep(50); } catch (InterruptedException e) {}
        synchronized (lockB) {   // ← DEADLOCK: T2 holds lockB
            System.out.println("T1 acquired both locks");
        }
    }
});

// Thread 2: acquires lockB, then waits for lockA
Thread t2 = new Thread(() -> {
    synchronized (lockB) {
        System.out.println("T2 holds lockB, waiting for lockA");
        try { Thread.sleep(50); } catch (InterruptedException e) {}

            System.out.println("T2 acquired both locks");
        }
    }
});
t1.start(); t2.start();

Deadlock Prevention — Lock Ordering 

// FIX: always acquire locks in the same canonical order
void transfer(Account a, Account b, double amt) {
    Account first  = a.id < b.id ? a : b;   // consistent order by ID
    Account second = a.id < b.id ? b : a;
    synchronized (first) {
        synchronized (second) {
            first.balance  -= amt;
            second.balance += amt;
        }
    }
}

Deadlock Avoidance — tryLock with Timeout 

boolean acquireBothOrFail(ReentrantLock l1, ReentrantLock l2)
        throws InterruptedException {
    if (l1.tryLock(50, TimeUnit.MILLISECONDS)) {
        try {
            if (l2.tryLock(50, TimeUnit.MILLISECONDS)) {
                try {
                    doWork();
                    return true;
                } finally { l2.unlock(); }
            }
        } finally { l1.unlock(); }
    }
    return false;   // couldn't get both; caller can retry with backoff
}

CountDownLatch

Allows one or more threads to wait until a set of operations completes. Count starts at N, decremented by countDown() . Cannot be reset. 

CountDownLatch latch = new CountDownLatch(3);   // 3 workers must finish

for (int i = 0; i < 3; i++) {
    final int id = i;
    new Thread(() -> {
        try {
            doWork(id);
        } finally {
            latch.countDown();   // decrement; never skip — use finally
        }
    }).start();
}

latch.await();                // main thread blocks until count reaches 0
System.out.println("All workers done!");
// Optional: latch.await(5, TimeUnit.SECONDS)  — with timeout

CyclicBarrier

N parties each call await() ; all block until all N have arrived, then are released together. Can be reused for multiple phases. 

CyclicBarrier barrier = new CyclicBarrier(3, () ->
    System.out.println("=== Phase complete, all threads proceed ===")
);

Runnable worker = () -> {
    try {
        doPhase1();
        barrier.await();   // wait for all 3 to reach this point
        doPhase2();
        barrier.await();   // barrier reused for phase 2!
    } catch (BrokenBarrierException | InterruptedException e) {
        Thread.currentThread().interrupt();
    }
};

Part 5 — Generics

5.1

Why Generics?

Before generics (Java 1.4 and earlier), collections stored everything as Object . This worked, but forced you to cast on every retrieval and pushed type errors to runtime . Generics, introduced in Java 5 , move those errors to compile time .

✘ Pre-Generics (Java 1.4)
Java Raw List — ClassCastException lurking 
List names = new ArrayList();
names.add("Alice");
names.add("Bob");
names.add(42);          // compiles! ⚠️

for (Object o : names) {
    // Mandatory cast:
    String s = (String) o; // 💥 ClassCastException on 42
    System.out.println(s.toUpperCase());
}
✔ With Generics (Java 5+)
Java Typed List — error at compile time 
List<String> names = new ArrayList<>();
names.add("Alice");
names.add("Bob");
// names.add(42); ← COMPILE ERROR ✓

for (String s : names) {
    // No cast needed:
    System.out.println(s.toUpperCase());
    // Always safe ✓
}

Three Core Benefits of Generics

Benefit What It Means Example
Compile-time type safety Type mismatches caught by the compiler, not at runtime List<String> rejects add(42)
Elimination of casts No explicit (Type) casting needed on retrieval String s = list.get(0)
Reusability Write one algorithm/class that works for many types Comparable<T> , Optional<T>
◆ Key Concept — Compile-time Feature Only

Generics are a compile-time feature only. At runtime, all type parameters are erased — List<String> and List<Integer> are both just List in the JVM. This is called type erasure and is covered in depth in Section 5.6.

Bounded Type Parameters

Bounds restrict which types can be substituted for a type parameter. An upper bound ( extends ) says "T must be a subtype of X". This also lets you call X's methods on values of type T.

// With upper bound — T is a Number, .doubleValue() is available

    double result = 0;
    for (T t : list)

// Find the maximum element in any List of Comparable elements
public static <T extends Comparable<T>> T max(List<T> list) {
    if (list.isEmpty())
        throw new NoSuchElementException("Empty list");

    T result = list.get(0);
    for (int i = 1; i < list.size(); i++) {
        if (list.get(i).compareTo(result) > 0)
            result = list.get(i);
    }
    return result;
}

A wildcard ? represents an unknown type. Unlike type parameters (which name a type for reuse), wildcards are used in method signatures where you don't need to reference the specific type by name. They provide flexibility at use-site.

sumList(List.of(1, 2, 3));          // List<Integer> ✓
sumList(List.of(1.5, 2.5));         // List<Double>  ✓
sumList(List.of(1L, 2L, 3L));       // List<Long>    ✓

3. Lower-Bounded Wildcard — <? super Integer>

Accepts a list of Integer or any supertype ( Number , Object ). You can add Integer values but can only read as Object (contravariant — safe consumer).

Java 
public static void fillIntegers(List<? super Integer> list, int n) {
    for (int i = 0; i < n; i++)
        list.add(i);     // ✓ adding Integer is always safe
}

List<Integer> ints    = new ArrayList<>();
List<Number>  numbers = new ArrayList<>();
List<Object>  objects = new ArrayList<>();

fillIntegers(ints,    3);  // ✓  ? super Integer includes Integer
fillIntegers(numbers, 3);  // ✓  Number is a supertype of Integer
fillIntegers(objects, 3);  // ✓  Object is a supertype of Integer

The PECS Principle — Producer Extends, Consumer Super

Mnemonic Wildcard You can You cannot Use case
P roducer <? extends T> Read as T Add (except null) Reading/consuming from a collection
C onsumer <? super T> Add T or subtype Read as anything except Object Writing/adding to a collection
Both <T> (type param) Read and write — Need to both read and write
Java PECS in action — Collections.copy() 
// src is a PRODUCER (we read from it)   → extends
// dest is a CONSUMER (we write into it) → super
public static <T> void copy(
        List<? super T>   dest,
        List<? extends T> src) {
    for (int i = 0; i < src.size(); i++)
        dest.set(i, src.get(i));
}

Why List<Dog> is NOT a subtype of List<Animal>

Generics are invariant . Even though Dog extends Animal , List<Dog> is not a subtype of List<Animal> . This prevents a category of type-safety bugs that plague arrays.

✘ Arrays (covariant) — unsafe!
Java 
Dog[] dogs = new Dog[2];
Animal[] animals = dogs;   // ✓ compiles
animals[0] = new Cat();   // compiles!
// 💥 ArrayStoreException at RUNTIME
// because dogs[0] is actually a Cat
✔ Generics (invariant) — safe!
Java 
List<Dog> dogs = new ArrayList<>();
// List<Animal> a = dogs;
// ← COMPILE ERROR ✓
// Type safety enforced at compile time

// Use wildcard for flexibility:
List<? extends Animal> a = dogs; // ✓
// but a.add(new Cat()); ← error ✓
ℹ Arrays vs Generics Variance Summary

Arrays are covariant: Dog[] IS-A Animal[] — but this can cause ArrayStoreException at runtime.
Generics are invariant: List<Dog> is NOT a List<Animal> — prevents the problem entirely at compile time.
Wildcards add back flexibility: List<? extends Animal> accepts a List<Dog> safely.

5.6

Type Erasure

Type erasure is the mechanism by which the Java compiler removes all generic type information from the compiled bytecode. At runtime, the JVM sees only raw types. This was a deliberate design choice to maintain backward compatibility with pre-Java-5 code.

┌────────────────────────────────────────────────────────────────────────┐ │ TYPE ERASURE PIPELINE │ ├────────────────────────────────────────────────────────────────────────┤ │ │ │ Source Code Compiler Step Bytecode (JVM) │ │ │ │ List<String> ─────────────────────────────▶ List (raw) │ │ Box<T> ──► T replaced by Object ─────▶ Box (Object field) │ │ <T extends ──► T replaced by first ─────▶ raw bound type │ │ Number> bound (Number) │ │ │ │ + Type casts inserted at call sites by compiler │ │ + Bridge methods generated for generic subclasses │ └────────────────────────────────────────────────────────────────────────┘

Before Erasure (source)

Java 
public class Box<T> {
    private T value;

    public T get() {
        return value;
    }
    public void set(T v) {
        this.value = v;
    }
}

Box<String> b = new Box<>();
b.set("hello");
String s = b.get();

After Erasure (bytecode equivalent)

Java 
public class Box {          // raw
    private Object value;    // T → Object

    public Object get() {    // T → Object
        return value;
    }
    public void set(Object v) {
        this.value = v;
    }
}

Box b = new Box();
b.set("hello");
String s = (String) b.get(); // cast inserted

Bridge Methods

When a generic class is subclassed with a concrete type, the compiler generates a synthetic bridge method so that polymorphism works correctly.

Java Bridge method generation 
// Source code
class StringBox extends Box<String> {
    @Override
    public void set(String v) { super.set(v); }
}

// After erasure — compiler also generates a BRIDGE METHOD:
// public void set(Object v) { set((String) v); }  ← synthetic bridge
// This allows: Box b = new StringBox(); b.set("x"); to work via polymorphism

new T[10] Array creation requires a concrete type at runtime Use @SuppressWarnings with (T[]) new Object[10] , or use List<T> instead

// ✗ Cannot do: new T()
// ✓ Workaround — pass a Supplier or Class<T>
public class Factory<T> {
    private final Supplier<T> supplier;

    public Factory(Supplier<T> supplier) {
        this.supplier = supplier;
    }
    public T create() { return supplier.get(); }
}
Factory<ArrayList> f = new Factory<>(ArrayList::new);

// ✗ Cannot do: obj instanceof T
// ✓ Workaround — Class<T> token
public <T> boolean isInstanceOf(Object obj, Class<T> cls) {
    return cls.isInstance(obj);  // ✓
}

// ✗ Cannot do: new T[n]
// ✓ Workaround — cast + suppress (use with caution)
@SuppressWarnings("unchecked")

    return (T[]) new Object[n];  // heap pollution — prefer List<T>
}
💡 Tip — Class<T> as a Type Token

To retain type information at runtime despite erasure, pass a Class<T> object (called a type token ). Libraries like Guava and Jackson use this pattern extensively. For complex generic types, use TypeReference<T> (also called a super type token ) to capture parameterized types like List<String> at runtime.

5.7

Static Members & Generic Exceptions

Two common sources of confusion: static members interacting with class-level type parameters, and how erasure affects generic exception handling.

Static Fields Cannot Use Class Type Parameter

The class type parameter T belongs to each instance of Box<T> . A static field is shared across all instances and thus cannot be typed as T .

Java Static field restriction 
public class Box<T> {

    // ✗ COMPILE ERROR — static field cannot use class type param
    private static T defaultValue;

    // ✓ OK — static field with concrete type
    private static int instanceCount = 0;

    // ✗ COMPILE ERROR — static method cannot reference T from class
    public static T getDefault() { ... }

    // ✓ OK — static method with its OWN type parameter
    public static <E> Box<E> of(E value) {
        return new Box<>(value);     // factory method
    }
}

// The static method declares its own <E>, completely independent of class T
Box<String> sb = Box.of("hello");   // E inferred as String
Box<Integer> ib = Box.of(99);       // E inferred as Integer

Generic Exceptions — What Is and Isn't Allowed

Due to type erasure, catch clauses work on raw types at runtime. This creates several restrictions on generics and exceptions.

Java Generic exception rules 
// ✗ Classes extending Throwable CANNOT be generic
class GenericException<T> extends Exception { }   // COMPILE ERROR
class GenericError<T> extends Throwable { }       // COMPILE ERROR

// ✗ Cannot catch a type parameter
public <T extends Exception> void bad() {
    try { ... }
    catch (T e) { }  // COMPILE ERROR
}

// ✓ CAN: Throw a type parameter (in try/catch context)
public <T extends Exception> void good(T ex) throws T {
    throw ex;   // ✓ allowed — useful for checked exception wrapping
}

// ✓ CAN: Non-generic exception with generic FIELDS
class DataException extends RuntimeException {
    private final List<String> errors;  // generic field ✓

    public DataException(List<String> errors) {
        super("Validation failed: " + errors);
        this.errors = errors;
    }
    public List<String> getErrors() { return errors; }
}

// ✓ CAN: Use generic type parameter as thrown type
interface Processor<T, E extends Exception> {
    void process(T item) throws E;   // ✓ generic checked exception
}

Construct Allowed? Reason / Workaround

Static method using class T ✗ NO Declare a separate <E> in the method signature.
Static generic method with own <E> ✓ YES Method-level type param is independent of class type param.
class Foo<T> extends Exception ✗ NO JLS prohibits generic Throwable subclasses due to erasure.

5.8

Raw Types & Best Practices

A raw type is a generic class or interface used without any type arguments. They exist solely for backward compatibility — avoid them in new code . Using raw types opts you out of generic type checking and can lead to heap pollution .

✘ Raw Type — Avoid!
Java 
// Raw type — generates "unchecked" warnings
List list = new ArrayList();
list.add("hello");
list.add(42);    // ⚠️ no error!

// Heap pollution:
List<String> typed = list;  // unchecked warning
String s = typed.get(1); // 💥 ClassCastException
✔ Parameterized Type — Correct
Java 
// Fully parameterized
List<String> list = new ArrayList<>();
list.add("hello");
// list.add(42); ← COMPILE ERROR ✓

// No cast needed, no surprise:
String s = list.get(0); // always String ✓
// Clean, safe, self-documenting

Heap Pollution & @SuppressWarnings

Heap pollution occurs when a variable of a parameterized type refers to an object that is not of that type — usually caused by mixing raw types and parameterized types, or by unchecked casts.

Java Heap pollution example and suppression 
// This method causes heap pollution:
@SafeVarargs                             // suppress varargs heap pollution warning
public static <T> List<T> listOf(T... items) {
    return Arrays.asList(items);
}

// @SuppressWarnings("unchecked") — when is it acceptable?
@SuppressWarnings("unchecked")
public T[] toArray(int size) {
    // ✓ OK to suppress ONLY when you have proven the cast is safe
    // AND you document WHY it's safe:
    // "Safe because this array is only used internally as T[]"
    return (T[]) new Object[size];
}

// ✓ Scope suppression as NARROWLY as possible
// Annotate the variable, not the whole method:
@SuppressWarnings("unchecked")
T[] result = (T[]) new Object[size];  // narrow scope ✓
